# 03 — Authentication Flow (Supabase Auth)

Status: **Draft for review** · Related: [01-architecture](./01-architecture.md), [02-database](./02-database.md)

## 1. Decisions

| Topic | Decision |
| --- | --- |
| Provider | Supabase Auth, email + password (free). OAuth providers can be added later at no cost. |
| Library | `@supabase/ssr` + `@supabase/supabase-js` |
| Session storage | Cookies set by the server with **`httpOnly: true`, `secure: true` (prod), `sameSite: 'lax'`, `path: '/'`** |
| Session refresh | `proxy.ts` (Next.js 16 renamed `middleware.ts` → `proxy.ts`) |
| Server identity check | `supabase.auth.getUser()` (validates the JWT with Supabase) — **never trust `getSession()` on the server** |
| Email confirmation | Enabled. Link → `/auth/callback?code=...` → `exchangeCodeForSession` |

### 1.1 Why HttpOnly works with direct uploads

HttpOnly cookies mean the browser JavaScript cannot read the session, so the browser has **no** authenticated Supabase client. That is intentional (XSS cannot steal tokens). Everything that needs identity runs on the server. The one browser → Supabase call — image upload — uses a **signed upload URL** generated by a Server Action with the user's session (see 01-architecture §4), so it needs no session in the browser.

## 2. Supabase Clients

| File | Used in | Cookies |
| --- | --- | --- |
| `lib/supabase/server.ts` | Server Components, Server Actions, Route Handlers | `createServerClient` with `cookies()` from `next/headers`; `setAll` forces `httpOnly`, `secure`, `sameSite` |
| `lib/supabase/proxy.ts` | `proxy.ts` | Reads cookies from `NextRequest`, writes refreshed cookies to `NextResponse` with the same forced options |
| `lib/supabase/browser.ts` | Client Components (uploads only) | `createBrowserClient` with anon key, **no session**; only `uploadToSignedUrl` is allowed |

Setting cookies from a Server Component throws; `setAll` wraps it in `try/catch` (the proxy already refreshed them).

## 3. Flows

### 3.1 Register — `/register`

Form fields: `email`, `password` (min 8), `displayName`, `accountType` (`customer` | `merchant`), `storeName` (required if merchant).

```
Server Action signUp(formData)
  1. Zod validate (storeName required when accountType = merchant)
  2. If merchant: check store name availability
        select 1 from profiles where lower(store_name) = lower($1)   -- merchant profiles are public
  3. supabase.auth.signUp({ email, password, options: {
        emailRedirectTo: `${SITE_URL}/auth/callback?next=/dashboard`,
        data: { display_name, role: accountType, store_name } } })
  4. Trigger handle_new_user creates the profile (see 02-database §4)
  5. Return { data: { needsEmailConfirmation: true }, error: null }
     → UI shows "Check your email"
```

The `role` sent in metadata is user-controlled, which is acceptable: self-service merchant sign-up is a product requirement. The trigger only honours it when a valid, available `store_name` is present.

### 3.2 Email confirmation — `app/auth/callback/route.ts`

`GET ?code&next` → `exchangeCodeForSession(code)` → redirect to `next` (only relative paths starting with `/` are allowed, to prevent open redirects) or `/login?error=confirmation_failed`.

### 3.3 Login — `/login`

```
Server Action signIn(formData)
  1. Zod validate
  2. supabase.auth.signInWithPassword(...)   → server client sets HttpOnly cookies
  3. Generic error on failure: "Invalid email or password" (no user enumeration)
  4. redirect(next ?? '/dashboard' for merchants, '/' for customers)
```

### 3.4 Logout

Server Action `signOut()` → `supabase.auth.signOut()` → `redirect('/')`. Rendered as a `<form action={signOut}>` button (POST, so it cannot be triggered by a link/prefetch).

### 3.5 Become a merchant (existing customer, or merchant whose store name was taken at sign-up)

`/dashboard/onboarding` → Server Action `becomeMerchant({ storeName })` → `supabase.rpc('become_merchant', { p_store_name })`. Error code `23505` → "Store name already taken".

## 4. Route Protection

### 4.1 `proxy.ts` (optimistic, runs on every matched request)

```
matcher: all paths except _next/static, _next/image, favicon.ico, and image files

1. updateSession(request): create proxy client, call supabase.auth.getUser() → refreshes cookies
2. If path starts with /dashboard and no user → redirect /login?next=<path>
3. If path is /login or /register and user exists → redirect /dashboard
4. Return the response carrying refreshed cookies (must not be replaced by a new NextResponse)
```

The proxy does **not** query `profiles` (keep it fast). Per Next.js docs, the proxy is not a full authorization layer.

### 4.2 Server-side authorization (authoritative)

| Location | Check |
| --- | --- |
| `app/dashboard/layout.tsx` | `getUser()`; no user → `redirect('/login')`. Load profile; `role !== 'merchant'` → `redirect('/dashboard/onboarding')` (except on the onboarding page itself). |
| Every Server Action | Starts with `const user = await requireUser()`; merchant actions use `requireMerchant()`. Returns `{ data: null, error: 'Unauthorized' }` instead of throwing. |
| Database | RLS is the final guard even if app checks have a bug. |

Helpers (`lib/auth.ts`):
- `getCurrentUser(): Promise<User | null>`
- `requireUser(): Promise<User>` — redirects to `/login` in pages
- `getCurrentProfile(): Promise<Profile | null>`
- `requireMerchant(): Promise<{ user: User; profile: Profile }>`

## 5. Supabase Dashboard Settings (manual, free)

- Authentication → URL Configuration: Site URL = production URL; Redirect URLs = `http://localhost:3000/auth/callback`, `https://<vercel-domain>/auth/callback`.
- Authentication → Providers → Email: confirm email **on**, minimum password length 8.
- Built-in SMTP is rate-limited; for more volume later, a free SMTP tier can be configured (no code change).
